# شمس الخير — تسليم هندسي لتوحيد المراحل الست وتدقيق الإطلاق

## ماذا أصلحنا الآن؟

هذه حزمة *الكود الموحّد* للمراحل الست، مع إصلاحات أمنية/مالية بعد المرحلة السادسة؛ ليست موقعًا إنتاجيًا منشورًا ولا ادعاء بأن جميع الخدمات تعمل.

- تعديل `/api/stage6` ليكتب العملية وسجل التدقيق ضمن **معاملة PostgreSQL واحدة** في: الفواتير، المدفوعات، الشهادات، الموافقات والإلغاء، الاختبارات، المراجعات، نقاط التحفيز، الجدولة. يجب مراجعة بقية مسارات المراحل 1–5 بالطريقة نفسها قبل الإنتاج.
- وضع معرف طلب UUID فريد `idempotencyKey` على المدفوعات اليدوية في جداول `MenPayment` و`WomenPayment` و`AcademyPayment` لمنع تكرار الدفعة عند تكرار الطلب نفسه. كل تكرار بنفس البيانات يعيد رقم الإيصال، أما إعادة استخدام المعرّف ببيانات مختلفة فترفض.
- إلغاء `UPDATE`/`DELETE` على جداول المدفوعات من صلاحيات موظفي التشغيل في `db/roles-stage6.sql` (دفتر تحصيل إضافي غير قابل للتعديل من التطبيق؛ تصحيح الأخطاء المالية يحتاج إجراء تعويض معتمد).
- حقْل مستقل في واجهة الدفع لقيمة المبلغ المقبوض بدل إعادة استخدام قيمة إنشاء الفاتورة.
- `GET /api/health` لا يُرجع كلمات المرور أو البيانات الشخصية؛ يفحص اتصال أدوار قاعدة البيانات المحدودة.
- `scripts/verify-integration.mjs` يفحص بنية الملفات وصياغة TypeScript وتهيئة البيئة دون كشف الأسرار.
- `scripts/verify-db-isolation.mjs` لا يغيّر أي بيانات، ويتحقق من أن قاعدة البيانات التجريبية تسمح لكل دور بقراءة جداول قسمه فقط.

## ما تم اختباره بالفعل في بيئة إعداد الملفات

- `node --test tests/*.test.mjs`: **67/67 اختبارًا ناجحًا**؛ منها خمسة اختبارات تنفيذية لوظيفة تسجيل الدفع باستخدام معاملات وهمية، والبقية اختبارات منطقية/بنيوية ولا تمثل تكاملًا حقيقيًا.
- `node scripts/verify-integration.mjs`: فحص صياغة **104 ملف TypeScript/TSX دون أخطاء نحوية** (وليس فحص أنواع TypeScript).
- `node scripts/verify-integration.mjs --strict`: **فشل كما ينبغي** بسبب غياب حزم npm وبيانات اتصالات قاعدة البيانات في بيئة الإعداد.
- لا تتوفر لدينا في هذه البيئة إمكانية الوصول إلى npm أو تثبيت PostgreSQL، **ولم تنفَّذ** `prisma validate`, `prisma generate`, `prisma migrate`, `tsc --noEmit`, `next build`, أو اختبارات قاعدة البيانات الفعلية.

## خطوات تشغيل نسخة موحدة على جهاز التطوير

**نفّذ على PostgreSQL تجريبية جديدة خالية من بيانات المدرسة الحقيقية.** يلزم Node.js 22 وPostgreSQL 17 وnpm واتصال إنترنت وتكوين حسابات تشغيل محدودة.

1. فك ضغط الحزمة وانسخ `.env.example` إلى `.env` للإعداد المحلي فقط. أضف قيم المرحلة 2–5 الموجودة في `.env.runtime.example` دون نسخ كلمة مرور مدير القاعدة لبيئة الموقع.
2. أنشئ قاعدة بيانات **جديدة باسم اختباري** `shams_alkhair_test`؛ لا تستخدم قاعدة إنتاج ولا تنسخ بيانات أطفال حقيقية.
3. في مجلد المشروع شغّل `npm install` ثم `npx prisma validate` و`npx prisma generate`.
4. على القاعدة التجريبية *الجديدة فقط* شغّل `npx prisma migrate dev --name unified_initial`. مستودع المشروع الأصلي **لا يحتوي سجل migrations مُعتمد للإنتاج**؛ يتطلب أي تحديث لقاعدة موجودة خطة ترحيل منفصلة ومراجعة نسخ احتياطي واستعادة.
5. طبّق ملفات القيود SQL بالترتيب `constraints.sql` ثم `constraints-stage2.sql` ... حتى `constraints-stage6.sql`، ثم ملف الصلاحيات `roles.sql` وبعده `roles-stage2.sql` ... `roles-stage6.sql` بواسطة مدير قاعدة البيانات **قبل استقبال أي طلب كتابة**.
6. أنشئ أدوار LOGIN محدودة، ومختلفة لكل نطاق، واربطها بأدوار SQL المناسبة؛ لا تضع حساب `postgres` داخل `DATABASE_URL_STAFF_*` أو `DATABASE_URL_MEN/WOMEN/...`.
7. اجعل متغيرات التشغيل تُشير إلى القاعدة التجريبية وتأكد من اختلاف أسماء مستخدمي SQL. ثم شغّل:

```bash
npm run db:seed
npm run verify:offline
npm run verify:strict
CONFIRM_TEST_DATABASE=YES npm run verify:db-isolation
npm run typecheck
npm run build
npm run dev
```

8. اختبر `http://localhost:3000/api/health` (200 يعني الاتصالات الثمانية تعمل، 503 يعني متغيرات ناقصة أو تعذّر الاتصال). ثم جرّب تسجيل زائر وهمي؛ حجز اختبار؛ اعتماد طالب وهمي؛ إنشاء حلقة؛ إصدار كارت QR؛ تسجيل حضور؛ تقرير ولي أمر؛ إصدار فاتورة؛ تسجيل تحصيل بنفس مفتاح الطلب مرتين؛ شهادة خاصة؛ وتحقق عام لا يكشف أي بيانات شخصية.
9. اختبر اختبارات التكامل على قاعدة **تجريبية فقط** حسب ملفات `scripts/*smoke.mjs` مع حسابات وهمية وإعدادات تأكيد الاختبارات.

## شروط منع الإطلاق الحقيقي

لا تُفعِّل استقبال بيانات الطلاب حتى تصبح جميع النتائج السابقة ناجحة، وتُراجع الواجهة على الموبايل، وسياسة الخصوصية، والتفويض والصلاحيات، والموافقات على تسجيلات الأطفال، والتشفير، والنسخ الاحتياطي واستعادة البيانات، والرقابة على التغييرات، والإشعارات وCloudflare وASR بشكل مناسب. يجب استكمال **ترحيل البيانات القديمة** إن وُجدت قبل اعتماد عمود `idempotencyKey` الإلزامي.

الفيديوهات وASR وواتساب والدفع الإلكتروني وتطبيق Android/iOS ليست خدمات مُفعّلة في هذه الحزمة. روابط Vercel السابقة **معاينات واجهات منفصلة**، ولا تمثل نسخة موحّدة متصلة بقاعدة بيانات.

### أولويات هندسية قبل الإنتاج

1. تنفيذ واختبار Migrations مع نسخ احتياطي فعلي على PostgreSQL تجريبي.
2. اختبارات E2E بحسابات محاكاة وإثبات عزل النساء عند مستوى DB والمخزن والـAPI.
3. توحيد معاملات التدقيق في **بقية** مسارات المشروع وليس المرحلة السادسة فحسب.
4. معالجة التعارضات والمصادقة وRate Limiting والنسخ والاستعادة والتحقق من الصلاحيات على خادم فعلي.
5. اختبار عملية الدفع المالي اليدوي وحالات رفض/إلغاء الشهادات والفيديوهات.
6. نشر **نسخة staging واحدة حقيقية** ببيانات وهمية وراء تسجيل دخول محمي، ثم اختبارها، وبعدها فقط التخطيط للإطلاق الفعلي.
